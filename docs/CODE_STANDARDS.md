# AI Trading 代码规范

本规范用于当前 Next.js、FastAPI 与独立 Collector 项目。目标是让开发者能够顺着
代码理解请求、状态变化和持久化过程。规范参考用户提供的 Word 文件，经本项目
实际工具链和 Docker 工作方式调整后，以此文件作为可执行版本。

## 通用原则

正确性优先，其次是可读性、简单性和可维护性。性能优化应有具体瓶颈或任务要求。
不为少写几行代码牺牲表达，也不为显得规范增加多余层次。

- 一个函数围绕一个可命名的职责组织。校验、数据库操作、重试和界面渲染混杂时，
  按真实职责分开；不使用机械行数限制，也不拆成大量一行函数。
- 简单条件优先 early return。复杂状态用明确分支或状态映射，避免嵌套三元表达式。
- 变量用业务名称，例如 `channelSource`、`collectorStatus`、`sourceConfiguration`。
  `response`、`connection` 等具有明确上下文的通用名称可以保留，不设置词语黑名单。
- Boolean 优先 `isConnected`、`hasError`、`shouldRetry`；Python 使用对应 snake_case。
  已有 API 字段如 `enabled`、`process_alive` 保持兼容，不仅为命名修改外部协议。
- helper 必须表达可理解的业务步骤或实际复用；单次调用不是禁令，但仅转发参数、
  隐藏副作用或需要频繁跳转才能理解的 helper 应删除。
- 每个手写源码文件和每个函数都提供中文注释，帮助理解职责、流程和副作用；
  具体格式见下方“注释要求”，不能用命名清晰为理由省略。
- 不吞异常。仅在能重试、转换为领域错误、记录脱敏状态或释放资源的边界捕获。

## 修改范围

先阅读相关实现、测试和文档，保留架构与现有行为。用户明确要求重构时，可按职责
调整相关模块；不能同时增加无关功能、改数据结构或更换运行环境。历史迁移不因
可读性整理而改变操作；本次按用户要求补充说明注释。样式没有设计变更时保留视觉效果，避免整库格式化制造噪音。

## UI 技术与适配范围（用户明确约定）

- UI 基础组件统一使用 **shadcn/ui**，本次就迁移现有面板。按钮、表单输入、弹窗、
  表格、开关、状态标签等从 `frontend/components/ui/` 引用，不在业务页另写一套。
- shadcn/ui 的组件源码由项目维护。基础样式和变体在 `components/ui/` 集中修改；
  主题颜色、间距相关变量放在 `app/globals.css`，布局使用 Tailwind 工具类。
- `features/collector/` 保留来源表单、运行状态等业务组合组件；复用基础组件并不
  意味着把业务 UI 全部塞回一个页面。不要增加没有业务意义的包装组件。
- 仅在现有组件不能表达需求时写必要的自定义样式，并说明原因；不积累第二套按钮、
  输入框、弹窗和表格 CSS，不重复实现 shadcn 已提供的焦点及键盘交互。
- **当前只做 PC 端**，以桌面管理面板为验收目标（常用桌面宽度 1280–1920px）。
  暂不做手机/平板专用布局、折叠菜单或断点验收，功能完善后再安排多端适配。
  shadcn 自带的响应式类可以保留，但不为移动端额外定制或增加工作范围。

## 注释要求（用户明确约定）

- 每个手写源码文件开头用中文说明文件职责及其在流程中的位置。
- 每个函数、方法、React 组件和 Hook 都写中文说明。简单函数可用一句话；涉及
  请求、事务、轮询、重试或副作用时，补充输入含义、返回结果、失败处理或资源释放。
  不要求对 TypeScript/Python 类型已经表达清楚的每个参数再写重复说明。
- Python 使用模块/函数 docstring；TypeScript 使用文件说明和函数前的 JSDoc；
  CSS、Dockerfile、YAML、TOML、Makefile 等使用该格式支持的文件头注释。
- 匿名回调也要能读懂：简单 UI 绑定可在所属 JSX 区块说明；有业务步骤的回调使用
  具名函数或在回调前写注释。不要为满足注释数量机械拆出一行函数。
- 从 shadcn 加入后纳入维护的组件也补齐中文文件和函数说明，保留原有版权声明；
  后续 CLI 覆盖组件时核对并恢复这些说明。
- JSON 不加入非法注释；`package.json`、`tsconfig.json`、`components.json` 等的用途
  在 README 配置索引中说明。依赖锁文件、`next-env.d.ts`、编译输出、第三方依赖
  不手工注释。Markdown 的标题和开头说明承担文件介绍，无需隐藏注释。
- 注释必须随代码更新，禁止与实现不符或只写“处理逻辑”的空泛占位说明。

## 前端

- 路由页面负责组合功能，静态布局优先 Server Component；轮询、事件与表单集中在
  实际需要浏览器状态的 Client Component。不要为拆分边界反复传递难以理解的 props。
- 按功能组织采集面板：API 契约、请求、轮询 Hook、来源表单、来源列表、运行状态。
  不引入通用请求框架、状态管理库或单实现接口。
- API Client 处理 HTTP 与错误响应；Hook 管理轮询和请求生命周期；组件描述界面。
  不把这些逻辑长期放进一个页面函数。
- TypeScript 保持 strict，禁止显式 `any`。未知错误响应使用 `unknown` 并缩窄类型。
  不用 `as` 掩盖空值或缺失字段。自有 API 的响应以 FastAPI Response Model 为契约，
  前端声明对应类型；不复制一套庞大的运行时字段校验器。
- 表单模式使用明确的联合类型，例如 create 与 edit，不把对象、字符串和 null
  混在一起后依靠类型断言区分。
- 用户输入在边界校验：表单提供即时反馈，后端校验作为最终约束。不要在内部每个
  helper 中重复校验已经通过的字段。
- ESLint 使用 Next.js 官方 core-web-vitals 与 TypeScript 规则；Prettier 负责格式，
  TypeScript 负责类型。规则覆盖不能作为消除报错的捷径，例外必须有具体原因。
- 提取组件后保持可访问名称、加载态、空态和错误反馈；适配范围遵循 PC 端约定。

## 后端

- HTTP Router 负责 Depends、请求与响应契约、状态码和领域错误到 HTTP 的映射。
  不直接堆叠 SQL 查询，也不在应用工厂里定义全部业务闭包。
- Service 只在实际编排业务步骤时建立，例如“更新来源并记录事件”或“查询概览并
  解释心跳”。简单只读健康检查可以直接访问连接，不强制穿过三层。
- Repository 负责查询和写入。来源配置与审计事件需要同一事务时，Service 显式
  创建事务并传递 connection；Repository 不偷偷提交，也不隐藏启停等业务判断。
- Pydantic 用于消息/API 边界及确实需要的结构化记录。复用已有契约，不机械复制 DTO。
  内部状态优先具名字段；不能用元组下标编码“配置版本、可访问性、检查时间”。
- Collector 的 Discord 回调、来源订阅与校验、进程生命周期分别组织；重试次数、
  心跳周期和有效期使用具名常量，并在关键位置解释业务理由。
- 事务、幂等约束、失败后的状态必须显式可追踪。保留重复投递、旧快照、来源删除
  保留消息等既有行为，不因重构削弱它们。
- 日志记录阶段、ID、异常类别和可操作原因，不输出 Token、SQL 参数或原始异常载荷。
- 沿用现有 Ruff lint/format 与 pytest；本次不额外叠加第二套 Python formatter。

## 工具与验收

依赖锁文件必须更新，安装和检查都在 Docker 中执行。当前前端用 npm，不为照抄示例
切换到 pnpm；后端沿用 uv / Ruff。命令以 Makefile 为准：

```bash
make frontend-check
make backend-check
make quality
```

不能只安装工具而不运行。按变更覆盖类型检查、lint、格式检查、迁移一致性和相关测试；
界面重构还要检查浏览器操作与布局。不要编写只复述实现的测试来凑数量。

交付前审查实际差异，确认命名、职责、事务和错误路径都更容易理解。没有 Git 时采用
任务前源码快照对比，快照排除 `.env`、凭证、依赖目录和构建产物。
