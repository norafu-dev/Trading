# AI 自动交易 / 跟单系统：项目目标与规划

本文保存最初讨论的产品目标、技术选型和后续确认的约定，是理解整个项目的入口。
项目界面暂用名为 Signal Desk。当前实现只是完整系统的采集阶段，不能把采集面板
当作整个项目的最终范围。

## 项目目标

开发一个 AI 自动交易 / 跟单系统：从 Discord 中指定 Trader 的 Channel / Thread
实时采集交易消息，用 AI 将自然语言解析成结构化交易信号，再根据交易规则生成
Execution，最后通过 CCXT 接入 Bitget 自动执行交易。

先做 MVP，跑通端到端流程，再逐步拓展功能。当前开发顺序是先完成采集，积累一个
Trader 一段时间的真实消息，然后分析该 Trader 的表达风格，再设计和实现解析与执行。
“采集阶段可用”和“完整自动交易 MVP 可用”是两个不同的验收结果。

## 已确认的产品与开发约定

| 事项 | 用户已确定的方向 |
| --- | --- |
| Discord 采集 | 只能使用 selfbot，选用 `discord.py-self` |
| 采集范围 | 指定 Trader 的 Channel / Thread 消息，按作者过滤 |
| 来源配置 | 从前端面板填写频道 / Thread 和 Trader 作者信息 |
| 运行可见性 | 从前端查看 Collector 的运行情况 |
| 消息浏览 | Discord 式 PC 布局；左侧单行显示频道，支持自定义分组和拖拽排序 |
| 信号解析 | 先采集一个 Trader 一段时间的消息，再分析如何处理；不同 Trader 风格不同 |
| 交易所 | 使用 CCXT 接入 Bitget |
| 交易验证方式 | 后续用小额实盘验证；用户反馈模拟仓支持的种类较少，不以模拟仓作为默认验收路径 |
| 开发环境 | 从项目开始就使用 Docker，依赖、构建、运行和检查在容器内进行 |
| 前端 UI | 使用 shadcn/ui，基础组件和主题集中维护 |
| 适配范围 | 当前只做 PC 端，功能完善后再考虑其他端 |
| 代码可理解性 | 每个手写源码文件和函数都要有中文说明，具体例外见代码规范 |

小额实盘是后续执行阶段的方向，不表示当前采集阶段要接入或发出真实订单；金额、
交易规则和执行范围尚未确定。本文也不将这些未定参数补成默认值。

## 技术栈

| 层次 | 技术选型 | 当前落地情况 |
| --- | --- | --- |
| 前端 | Next.js、React、TypeScript | 已用于 PC 管理面板 |
| UI | shadcn/ui、Tailwind CSS | 已迁移现有面板 |
| 后端 API | FastAPI、Pydantic | 已用于来源配置与概览接口 |
| 数据库 | PostgreSQL | 已保存来源、原始消息、版本、运行状态与事件 |
| 数据访问 / 迁移 | SQLAlchemy、asyncpg、Alembic | 当前实现使用 |
| Queue / Cache | Redis | 总体选型已确定，尚未加入当前运行服务 |
| 后台任务 | Worker / Celery | 总体选型已确定，异步解析和执行任务尚未实现 |
| Discord 采集 | `discord.py-self` | 独立 Collector 已实现，真实登录和消息接收待验收 |
| AI 解析 | AI 模型及调用方式待确定 | 等待真实 Trader 样本，不提前固定模型、提示词和信号字段 |
| 交易所接入 | CCXT + Bitget | 尚未实现 |
| 环境编排 | Docker、Docker Compose | 已落地，服务从 Compose 启动 |
| 依赖与质量工具 | npm；uv、Ruff、pytest；ESLint、Prettier、TypeScript | 已落地 |

独立 Collector 目前是长期运行的 Python 进程，不是 Celery Worker。
Redis 和 Celery 仍属于总体技术规划；没有因为当前采集可以直接入库而取消它们。

## 分阶段实施与完成标准

以下是按已确认开发顺序整理的阶段规划；后续阶段的细节需要结合样本和规则再确定。

| 阶段 | 要完成的事 | 完成标准 / 当前状态 |
| --- | --- | --- |
| M1：采集基础 | Docker 框架、来源管理、实时采集、原始消息留存、Collector 状态 | 基础代码与本地回归已完成；仍需实际 Token、来源权限和真实消息验收 |
| M2：样本积累与分析 | 运行一个 Trader 的采集，整理一段时间的消息，分析表达风格和上下文 | 能用真实样本解释哪些是交易动作、哪些是讨论，以及哪些消息无法独立判断；采集时长和数量未预设 |
| M3：AI 信号解析 | 基于样本定义结构化信号、Trader 适配方式和解析任务 | 能从样本得到可追溯的结构化结果，明确无法解析或信息不足的情况；模型与字段待定 |
| M4：规则与 Execution | 用明确规则把结构化信号转换成可执行计划 | 每个计划能解释执行或不执行的原因；金额、仓位、合约类型等规则需先确定 |
| M5：Bitget 小额实盘闭环 | CCXT 接入、执行计划提交、订单结果与状态跟踪 | 能把消息、信号、执行计划和实际订单结果关联起来，完成受明确范围约束的小额实盘验收 |
| 后续拓展 | 更多 Trader、更多信号风格、更多功能和其他端适配 | 完整 MVP 跑通后再安排，不在采集阶段提前扩张 |

阶段名称用于组织后续工作，并不意味着已经建立了对应模块或数据表。

## 目前做到了哪里

已有 PC 面板、来源增改删和启停、作者过滤、实时新消息处理、幂等入库、消息版本
存储、Collector 心跳及运行事件。来源由面板写入数据库，连接成功的 Collector
定期热更新配置，停用或删除来源保留历史消息。

当前已在首次连接和会话恢复时按频道最后一条已保存消息进行有界近期补采，每个频道
最多读取 1000 条并继续按作者过滤。消息编辑 / 删除事件处理、持久化频道游标、超过
补采窗口的完整历史恢复、附件下载、样本导出、Redis / Celery、AI 解析、Execution
或交易所执行仍未实现。

消息浏览页已支持单行频道切换、频道搜索、自定义分组、拖拽排序、自动刷新和已入库
消息分页。消息作者显示来源配置中的 KOL 名字；界面不显示头像。附件图片与 Discord
Embed 的主要展示字段可以直接查看。

最近一次开发验收包含 Docker 构建、规范检查、26 项后端测试和 PC 浏览器检查。
这属于本地实现验收，不替代真实 Discord 采集验收。实时状态以管理面板为准。

## 后续需要决定的内容

- 用哪个 Trader 的样本，采集多久，以及如何整理文本、引用、图片和 Embed。
- Trader 是否需要各自的解析配置，如何处理跨消息上下文、修改指令和不完整消息。
- AI 模型、结构化字段、解析评价标准，以及不明确结果进入何种处理流程。
- Bitget 的交易市场、仓位模式、订单动作、小额金额和具体交易规则。
- Execution 的状态、重复信号处理、订单结果核对，以及任务失败后的恢复方式。

这些问题保留为待决策项；先积累真实消息，不预先假定所有 Trader 使用相同模板。
