# 采集可靠性与阶段验收

本文说明 2026-10-01 新增的消息变更监听、补采恢复及来源时效标识。当前仍是 M1，
不包含 AI 解析、执行规则或交易请求。

## 消息编辑和删除

使用 `discord.py-self` 的原始编辑、删除与批量删除事件，不依赖客户端消息缓存。
编辑事件只有部分字段时，合并已保存原文，不把缺失字段当作空正文。尚未保存的
消息读取完整消息后继续执行作者过滤；暂时读取失败记录警告，不冒充已采到新版本。
编辑快照继续遵守消息 ID / 版本指纹幂等和版本时间排序，原始版本完整保留。

删除事件记录在 `message_deletions`，同时标记已存消息，不删除原文、版本或 R2 图。
删除可以先于新消息入库；数据库事务锁串行同一消息的写入和删除，旧快照不能复活
已删除消息。消息页显示“已编辑”和“已删除 · 原文留存”。
事件选择依据：[discord.py-self 原始消息事件](https://discordpy-self.readthedocs.io/en/v2.1.0/api.html#discord.on_raw_message_edit)。

## 独立补采与恢复

`channel_checkpoints` 保存扫描断点、固定扫描目标、覆盖起点、失败次数和下次尝试时间。
新消息直接入库，不推进历史断点；只有已确认处理成功的历史消息才推进扫描断点。
历史任务从旧到新每页 100 条，扫描失败保留已完成前缀，重启继续原目标。
即使消息入库成功但游标提交失败，重新扫描也只会幂等重放，不跳过缺口。

新来源的初始化仍覆盖最近 1000 条频道消息，过滤不命中作者的消息不保存。
已有来源升级后从最早留存消息前开始复核，以尽量找回此前近期补采留下的缺口。
覆盖范围内的断线缺口没有总条数上限，持续分页；覆盖起点之前并非已验收的全量历史。
正常扫描完成后约 30 秒建立下一目标；失败采用 5/10/20…秒退避，上限 300 秒，持续重试。
每个频道的覆盖起点、最近完成时间和错误独立显示，不用连接状态代替补采完成状态。

目前单 Collector、单历史任务。没有增加 Redis 或第二个 Discord 会话。
更改作者规则不会自动重扫已经完成的范围；移除来源不会删除消息或历史扫描记录。

## 来源、延迟与时效

首次来源为 realtime / backfill / unknown；版本观察方式另记 edit。
重复投递不改变首次来源，编辑首次发现的旧消息归 backfill；升级前记录为 unknown，
不推测其来源。首次入库延迟由 first_seen_at 减原消息发布时间计算，最低为 0 秒。
时效提示以当前版本时间（编辑时间优先）计算，默认 120 秒，通过
`MESSAGE_FRESHNESS_SECONDS` 设置；它只是展示窗口，不能作为执行交易的授权。
历史补采即使仍在提示窗口内，也不能直接冒充实时新信号。

已加载的消息页会轮询复核，更新更早消息的编辑、删除和时效状态。翻页仍只读数据库。
后续 AI 模块需要独立任务、解析幂等、版本关系和时效规则，本次没有预建交易状态机。

## 验收及限制

Docker `make quality` 已通过前端 lint、格式、类型、生产构建，以及后端 Ruff、迁移
一致性和 73 项测试。测试覆盖超过千条积压、分页中断后重启、实时消息不推进历史断点、
首次千条范围、作者过滤、无缓存部分编辑、先删除后入库、并发删除、来源保持和时效提示。

本机数据库已升级到 `0007_collector_reliability`，升级前备份保存在
`/tmp/trading-before-collector-reliability.dump`（临时目录，不能替代长期备份）。
真实 Discord 连接恢复，4 个来源的本轮扫描均完成、无重试错误，新补回 44 条历史消息。
稳定图片接口读取并校验内容通过；PC 消息页还观察到自然到达的新消息显示“实时”。
这些结果验证当前连接、补采和展示，不代表已经验证外部编辑/删除事件或长期稳定性。

离线期间已删除且从未采到的正文无法恢复；已经扫描的较早消息在离线期间被编辑或
删除，当前不做全量核对，也不推测这些变更已采到。尚未留存消息的编辑读取失败时
有警告，但不保证恢复覆盖起点之前的该消息。真实外部编辑/删除事件仍需自然发生或
用户提供可控测试频道验证，不向用户的 Trader 频道发测试消息。
24–48 小时连续观察属于后续运行验收，自动化测试和短时连接正常不能代替它。
