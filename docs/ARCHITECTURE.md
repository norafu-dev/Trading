# AI Trading 系统架构

本文区分完整 MVP 的目标架构与当前已经运行的采集架构。
产品目标和已确认选择见 [PROJECT_OVERVIEW.md](PROJECT_OVERVIEW.md)，启动步骤见
[README.md](../README.md)。标为“计划”的模块尚不存在于当前运行链路。

## 完整 MVP 的业务流程

1. 用户在 Next.js PC 面板配置 Trader 对应的频道 / Thread 与作者。
2. 独立 Collector 使用 `discord.py-self` 接收消息，过滤来源并保存原始记录。
3. AI 解析模块根据 Trader 的样本分析结果，将自然语言转换为结构化信号。
4. 规则模块判断信号如何执行，生成 Execution，即带明确参数和处理状态的执行计划。
5. 交易执行模块通过 CCXT 向 Bitget 提交符合规则的订单。
6. 系统记录执行和订单结果，面板展示流程状态，能追溯到原消息和解析结果。

第 1、2 步已有基础实现；第 3–6 步是目标设计。原始消息、结构化信号、Execution
和交易所订单是不同层次的记录，不把“收到消息”直接等同于“应该下单”。

## 模块职责与技术边界

| 模块 | 职责 | 实现状态 |
| --- | --- | --- |
| Next.js PC 面板 | 来源配置、采集状态和原始消息展示；未来增加解析和执行可见性 | 当前仅实现采集相关功能，UI 使用 shadcn/ui |
| FastAPI | 接收面板请求，校验输入，调用服务层，返回明确的响应模型 | 已实现来源与概览 API |
| Collector | Discord 长连接、来源 / 作者过滤、原始消息标准化、持久化和心跳 | 已实现基础流程，独立于 API 运行 |
| PostgreSQL | 保存业务事实、配置、消息及状态；未来扩展信号和执行记录 | 已落地采集相关表 |
| Redis | 计划提供任务队列传递与必要缓存 | 尚未部署；不作为唯一业务事实存储 |
| Worker / Celery | 计划承接耗时解析及后续执行、状态核对任务 | 尚未实现；具体队列和任务拆分待设计 |
| AI 解析 | 结合 Trader 风格生成结构化信号，保留结果与原消息关联 | 待采样分析，模型与契约未定 |
| 规则与 Execution | 将信号转成确定的执行计划，并记录判定结果 | 待明确交易规则后实现 |
| CCXT / Bitget | 交易所 API 适配、订单提交与结果读取 | 计划使用小额实盘验证，当前未接入 |

当前先保持一个代码仓库中的清晰模块与独立运行进程，不预设每一层都要拆成独立
微服务。未来 Celery Worker 可以复用后端业务模块；API 不负责等待长时间 AI 请求
或交易所执行完成。具体任务拆分在对应阶段设计。

## 当前 Docker 运行架构

| Compose 服务 | 当前职责 |
| --- | --- |
| `web` | Next.js 生产构建，对本机开放 `127.0.0.1:3000`，同源代理 `/api` 到内部 API |
| `api` | 独立 FastAPI 进程，读取 / 写入 PostgreSQL，提供来源管理和概览接口 |
| `collector` | 独立 Python 进程，维护 Discord 会话、来源订阅、消息写入和心跳 |
| `postgres` | 持久化采集数据，使用命名卷保存数据 |
| `migrate` | 启动时运行 Alembic 迁移，完成后退出 |
| `test-postgres`、`tests` | 仅在 test profile 使用的隔离测试库与检查容器 |

API 和 PostgreSQL 不直接向宿主机开放端口。API 与 Collector 等迁移完成后启动，
Web 等 API 健康检查通过后启动。当前没有 Redis、Celery 或交易执行服务。

源码保存在宿主机项目目录，通过 Docker 构建进入镜像；Docker Desktop 应用目录
是运行工具的位置，不是项目源码目录。依赖安装、构建、运行、迁移和检查都在容器内完成。

## 当前采集与配置流程

### 来源配置

面板提交来源名称、频道 / Thread ID、作者 ID 列表和启用状态。FastAPI 校验输入后，
由来源 Service 在同一数据库事务中保存配置和审计事件。配置变化会重置校验状态。

Collector 在 Discord 就绪后约每 5 秒读取启用配置；对新增或修改的来源验证频道
可访问性并订阅。校验成功后才加载作者过滤规则，失败来源隔离并约每 30 秒重试。
同一频道可配置多个作者；父频道不自动包含子 Thread。

### 消息保存

Discord 新消息先按实际频道和作者过滤，再标准化为快照。当前消息和对应版本在
同一事务内写入 PostgreSQL。消息 ID 和版本指纹共同支持重复投递的幂等处理，旧
版本不能覆盖较新内容。首次连接和会话恢复后，Collector 以频道最后一条已保存消息
为断点读取最多 1000 条近期历史，再复用相同过滤和幂等写入链路。当前直接入库，
不经过 Redis；补采尚未使用独立的持久化频道游标，因此不能保证恢复超过窗口的缺口。

### 消息浏览

`/messages` 左侧以 Discord 式单行列表显示频道，用户可新建、重命名和删除分组，
也可拖拽频道改变归属和顺序；右侧提供只读消息区。`GET /api/messages/navigation`
合并自定义分组、当前来源与已保存消息，保留已移除来源的未分组历史入口。
`GET /api/messages` 按频道读取其中各作者的消息，用消息 ID 游标读取更早记录；ID 始终
以字符串传输，数据库按数值排序，前端使用 BigInt 合并，避免 Snowflake 精度丢失。

前端每 5 秒刷新，保留已加载的历史页和阅读位置。消息作者优先使用来源配置中的
KOL 名字；消息快照中的 Discord 昵称不会覆盖人工配置，界面不显示头像。分组、频道
归属和顺序保存到 PostgreSQL。附件和 Embed 仍来自原始 JSONB 快照，API 只暴露
Discord CDN / 代理媒体地址并转换为明确展示契约。分页不触发 Discord 补采。

### 运行可见性

Collector 将心跳、连接状态、最近写入时间和运行事件写入数据库。API 根据心跳
是否过期推导进程状态，面板约每 5 秒读取概览。进程存活、Discord 已连接和来源
校验成功分别表达；缺少 Token 时进程可以保持心跳，但不会连接 Discord。

## 数据边界

当前已有 `channel_groups`、`channel_sources`、`messages`、`message_versions`、
`collector_runtime`、`collector_events`。Discord ID 使用字符串，时间带时区。原始
内容与附件 / Embed 元数据留存，附件文件本身尚未下载。删除来源不删除已采集消息。

未来需要保存信号、解析记录、Execution 和交易所订单等业务事实，但表名、字段、
状态机与关联方式尚未定稿，不把这些概念写成已完成的数据库结构。

## 后续接入需要明确的设计

以下是进入后续阶段时需要完成的工程设计，不是已经实现的能力：

- 原始消息持久化与任务发布如何衔接，发布失败后如何发现和补发。
- Celery 重试或重复投递时如何避免重复解析和重复执行；不能只靠 Redis 锁判断是否下单。
- AI 输出如何校验，信息不足或语义模糊时如何处理；规则层不应猜测缺失的交易参数。
- Execution 如何记录执行意图和状态；交易所请求超时时，如何先核对结果再决定是否重试。
- 如何关联原消息、解析版本、执行计划与订单结果，方便排查每一步。
- Bitget 凭证如何在执行服务边界使用；前端不接收或显示密钥。

详细方案在样本分析、信号契约和交易规则确定后补充。当前先完成真实采集验收和
样本积累，不为这些待定设计预建空模块、假接口或不可验证的交易逻辑。
