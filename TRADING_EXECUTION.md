# AI Trading System — Trading Execution Design

> Status: learning/design in progress.
> This document records decisions already established. Items explicitly marked **TBD** are not yet final architecture.

## 1. Domain model

Do not collapse Signal, Execution, Order and Fill into one object.

```text
Signal
  ↓
Execution
  ↓
Order
  ↓
Fill
```

### Signal

Represents the Trader's interpreted trading intent.

Example:

```text
BUY BTC 20%
```

### Execution

Represents what the system intends to accomplish for a particular follower/user after applying allocation and risk rules.

Example:

```text
Buy $1,000 BTC for user X
```

### Order

Represents an actual order sent to the exchange.

One Execution may require multiple Orders.

Example:

```text
Execution target = $1,000

Order A = $600
Order B = $400
```

### Fill

Represents an actual exchange trade.

One Order may produce multiple Fills.

```text
Order = $1,000

Fill 1 = $300
Fill 2 = $400
Fill 3 = $300
```

Fills are historical facts and must not be destroyed merely because the parent Order was later cancelled.

## 2. Partial fills and cancellation

An Order can be cancelled after partial execution.

Example:

```text
Order target = $1,000
filled = $700
remaining = $300
status = CANCELLED
```

`CANCELLED` does not imply `filled = 0`.

Already-filled quantity is no longer reserved. Only quantity that can still execute needs to remain reserved.

Cancellation itself is asynchronous:

```text
cancelOrder()
↓
CANCEL_PENDING
↓
wait for WebSocket / REST confirmation
↓
CANCELLED / FILLED / other final truth
```

Do not release funds simply because the cancellation request was sent.

## 3. Exchange truth and local truth

For exchange execution facts:

> **Bitget is authoritative.**

PostgreSQL is the durable local record of those facts.

If local state conflicts with confirmed exchange state:

```text
query exchange
↓
confirm actual result
↓
synchronize PostgreSQL
```

Never mark an uncertain Order complete merely because a local worker completed.

## 4. UNKNOWN orders

The most dangerous situation is an ambiguous side effect.

Example:

```text
createOrder()
↓
Bitget creates order
↓
HTTP response is lost
↓
local system receives Timeout
```

The system does not know whether the order exists.

Therefore:

```text
createOrder Timeout / ambiguous 5xx
↓
Order = UNKNOWN
↓
keep local reserve
↓
query Bitget using clientOrderId
```

Outcomes:

```text
Order found
→ synchronize it
→ DO NOT submit again

Confirmed not to exist
→ retry may be considered

Still uncertain
→ remain UNKNOWN
→ continue reconciliation
```

Key rule:

> **Never blindly retry an ambiguous `createOrder()` result.**

## 5. Identifiers and idempotency

Maintain both internal and exchange identifiers.

Suggested concepts:

```text
execution_id
order_id                  # internal
client_order_id           # generated by this system
exchange_order_id         # Bitget order id
exchange_trade_id         # Bitget Fill/trade id
```

`exchange_trade_id` should be UNIQUE.

The same Fill may arrive through WebSocket and later through REST reconciliation. It must create only one Fill record.

## 6. WebSocket + REST architecture

CCXT/CCXT Pro can provide private WebSocket streams where supported by Bitget.

Conceptual responsibilities:

```text
Bitget
 ├─ REST
 │   ├─ place/cancel orders
 │   └─ reconciliation
 │
 └─ WebSocket
     ├─ order updates
     ├─ fills/trades
     ├─ balance updates
     └─ position updates
```

Application architecture:

```text
Trade Worker ───────────────┐
                            ↓
                          Bitget
                            ↑
Exchange WS Worker ─────────┤
                            │
Reconciliation Worker ──────┘

All durable business state
        ↓
   PostgreSQL
```

The Exchange WebSocket Worker should be a long-running service rather than a normal short-lived Celery task.

## 7. WebSocket disconnect recovery

A successful WebSocket reconnect does not prove that no events were missed.

```text
WS disconnect
↓
account state = UNTRUSTED
↓
WS reconnects
↓
REST reconciliation
  - unfinished orders
  - recent fills
  - balances when needed
  - positions
↓
repair PostgreSQL
↓
account state = HEALTHY
↓
resume trading
```

Key rule:

> **WS_CONNECTED != ACCOUNT_HEALTHY**

## 8. Reconciliation

Reconciliation repairs local state using exchange truth.

Prioritize Orders such as:

```text
OPEN
PARTIALLY_FILLED
CANCEL_PENDING
UNKNOWN
```

Typical process:

```text
fetch exchange state
↓
insert missing Fills idempotently
↓
recalculate Order filled quantity
↓
recalculate Order status
↓
recalculate Execution
↓
synchronize position / balance state
```

If a worker inserted a Fill but crashed before updating its Order, the next run should detect the existing Fill and rebuild the derived Order state instead of inserting the Fill again.

## 9. WebSocket / REST race conditions

Example:

```text
REST request begins
↓
WebSocket receives newer state
↓
WS transaction commits
↓
old REST response arrives
```

Do not use simple “last database writer wins”.

Protections:

- UNIQUE exchange Fill ID.
- Short database transactions.
- `SELECT ... FOR UPDATE` when modifying the same Order.
- Preserve exchange-side timestamps where available.
- Enforce legal state transitions.
- Never discard confirmed Fill facts because an older snapshot arrives.

Avoid:

```text
lock DB row
↓
wait on Bitget HTTP
```

Prefer:

```text
fetch Bitget
↓
open short DB transaction
↓
lock
↓
compare / merge
↓
commit
```

A terminal `FILLED` Order must not regress to `PARTIALLY_FILLED` merely because an older REST response arrives.

## 10. Balance and local reserve

Bitget balance is authoritative for exchange balance.

However, there is a local window before Bitget has accepted an intended Order.

Maintain a concept such as:

```text
exchange_available
local_pending_reserve
```

Example:

```text
Bitget available = $1,000
local_pending_reserve = $800

system available = $200
```

Once Bitget definitively accepts the Order, the exchange itself accounts for those funds and the corresponding local pending reserve can be released.

If `createOrder()` becomes UNKNOWN:

```text
keep local_pending_reserve
↓
reconcile
↓
determine whether Bitget accepted the order
```

Do not release it prematurely.

Normal operation should not synchronously REST-fetch balance before every order because this adds latency. Use trusted synchronized state on the fast path and reconciliation when trust decreases.

Cases that reduce balance/state trust include:

- WebSocket disconnect.
- UNKNOWN Order.
- Long-lived CANCEL_PENDING.
- Process/system restart.
- Detected local/exchange discrepancy.

Key rule:

> **Normal path optimizes for speed; abnormal path optimizes for certainty.**

## 11. Target State driven execution

Do not mechanically replay historical trading actions.

Example:

```text
10:00 BUY BTC 20%
10:03 CLOSE BTC
10:05 exchange recovers
```

Executing BUY then CLOSE after recovery is wasteful and may be dangerous.

Instead maintain the Trader's latest target state:

```text
target_position
target_version
```

Old queued work can detect that its version is stale:

```text
task target_version = 1
current target_version = 2

→ SUPERSEDED / STALE
→ do not create old Order
```

The core control concept is:

```text
Delta = Target Position - Actual Position
```

Example:

```text
Trader latest target = LONG 15%
actual follower position = LONG 12%

delta = +3%
→ increase by 3%
```

For direction changes:

```text
Actual = LONG 12%  (+12)
Target = SHORT 10% (-10)
```

Execution expresses the desired transition from `+12` to `-10`. The Order layer decides how to safely realize it, potentially closing the long position before opening the short position.

## 12. Target changes during execution

Before creating another position-changing Order, verify that the Execution's `target_version` is still current.

If the old Order has **not** been submitted:

```text
new target arrives
↓
old version becomes stale
↓
do not submit old Order
```

If the old Order **has already been submitted**:

```text
new target arrives
↓
cancel still-open old Order
↓
CANCEL_PENDING
↓
confirm final exchange Fill/state
↓
obtain latest Actual Position
↓
calculate delta against newest Target
↓
create necessary new Order
```

If `cancelOrder()` times out and WebSocket is unavailable:

```text
do NOT guess
↓
Order / account state becomes uncertain
↓
REST reconciliation
↓
confirm final Order / Fill / Position
↓
then calculate new action
```

## 13. Fill vs Actual vs Target

These answer different questions:

- **Fill**: What happened?
- **Actual Position**: Where are we now?
- **Target Position**: Where do we want to end up?

Do not simply reverse the amount of an old Fill.

The next action should normally be based on current Actual vs latest Target.

## 14. Retry / error classification learned so far

| Scenario | Handling | Reason |
| --- | --- | --- |
| Insufficient balance | Do not blindly retry; investigate balance/state | Same condition will usually fail again |
| 429 Rate Limit | Backoff + retry when no ambiguous side effect exists | Temporary restriction |
| `createOrder()` Timeout | UNKNOWN → reconcile by `clientOrderId` | Order may already exist |
| Ambiguous `createOrder()` 5xx | UNKNOWN → reconcile first | Side effect may already have occurred |
| Invalid symbol | Deterministic failure; no blind retry | Request cannot succeed unchanged |
| Market suspended/not tradable | Stop; refresh market metadata | Current market condition prevents execution |
| Below minimum order size | Skip/fail; do not automatically enlarge risk | System must not increase intended exposure |
| Invalid API key / permission denied | Disable trading for account + notify user | Account-level issue affects future orders |
| Exchange-wide outage | Circuit breaker | Prevent retry storms |

## 15. Circuit breaker

For exchange-wide failures, do not let every worker independently hammer Bitget.

States:

```text
CLOSED
normal

OPEN
pause new exchange trading requests

HALF_OPEN
allow a small number of safe probes
```

Use side-effect-free queries as recovery probes. Never use `createOrder()` as a health check.

After recovery:

```text
exchange reachable
↓
reconcile
↓
restore trusted account state
↓
revalidate queued Executions
↓
resume gradually
```

Do not blindly execute every task accumulated during the outage.

## 16. Revalidating delayed executions

A delayed Signal may no longer be valid.

Before executing backlog, re-evaluate deterministic conditions such as:

- Signal expiration.
- Current price deviation.
- Newer Trader Target.
- Current follower position.
- Current balance.
- Risk rules.

Example:

```text
Old target: BUY at market around 100,000
Exchange unavailable for 5 minutes
Current price: 103,000
```

The old action should not automatically execute simply because the queue retained it.

## 17. Pre-order validation

Catch deterministic failures before reserving funds whenever possible.

```text
Execution
↓
symbol exists?
market active?
spot/contract type correct?
amount/price precision valid?
minimum order requirements satisfied?
other static exchange rules satisfied?
↓
PASS
↓
fund check + reserve
↓
createOrder()
```

CCXT `load_markets()` can provide cached market metadata, but it is a snapshot and should be refreshed periodically/when exchange errors indicate it is stale.

Bitget remains the final authority on whether an order is accepted.

If intended size is below exchange minimum, do not automatically increase the position to satisfy the minimum.

## 18. Account-level authentication failures

Invalid API credentials or missing trade permission are different from a single failed Order.

```text
authentication/permission failure
↓
current operation fails
↓
account trading state = DISABLED / AUTH_ERROR
↓
stop subsequent new orders
↓
notify user
```

After credentials are repaired:

```text
validate API access
↓
fetch/reconcile account state
↓
confirm HEALTHY
↓
resume trading
```

## 19. Manual/external positions — deferred

If users trade manually in the same Bitget account, exchange total position may include both copy-trading and manual exposure.

Potential future concepts:

```text
copy_position
manual/external_position
manual_position_policy
```

Whether manual additions participate in later Trader CLOSE/REDUCE actions is a product decision.

**This topic is intentionally deferred and should not be assumed by implementation yet.**
